5. 缺陷清单（本次测试新发现）

共 18 项。P0 会造成数据错误或业务失真；P1 影响流程完整性；P2 为一致性与可信度问题。

P0-1
审核操作无幂等校验，重复点击即重复计分

auditRecord()（DutyContext.tsx:650）未校验记录当前状态。对一条 active 记录再次调用 approve，会再次执行 applyScoreDelta 扣分。 

实测复现：
  首次审核生效:  100 → 98
  重复审核:      98  → 96   ← 同一记录被扣两次
  （账实仍相符，但业务上属重复计分）

影响：管理员误操作或双端并发点击即造成分数错扣，教育场景下需向班主任解释，属于可被质疑的公平性问题。修复方向：auditRecord 入口增加 if (record.status !== 'pending_audit') return; 前置守卫。

P0-2
批量操作 ID 用 Date.now()，同毫秒必然碰撞

全项目 16 处 ID 生成为 id: \`xxx_${Date.now()}\`。而 syncOfflineDrafts()（DutyContext.tsx:636）用 forEach 同步循环调用 createRecord——同一 tick 内多个草稿拿到完全相同的时间戳。 

实测复现（5 条草稿同步）：
  生成 ID: rec_1760000000000 × 5
  唯一 ID 数: 1 / 应为 5   ❌ 确认碰撞

受影响实体：records / rectifications / appeals / notifications /
            shifts / dutyPosts / rules / ledger / drafts

影响：records.find(r => r.id === id)、map(r => r.id === id ? ...) 会命中错误对象，造成整改单挂到别的记录上、审核改错记录。离线同步是批量场景，100% 触发。修复方向：改用 crypto.randomUUID() 或自增序列。

P0-3
统计看板与工作台指标为硬编码假数据

DataAnalyticsView.tsx:42/51 写死「128 次」「94.2%」；AdminWorkbench.tsx:65 写死「82.5%」。而 records 实际仅 5 条 mock 数据，settlements.totalInspections 也是原型常量。

影响：演示时若被追问「这个 94.2% 怎么算的」无法回答；一旦接真实数据，界面仍显示旧数字，属信任崩塌型缺陷。修复方向：接入 ledger/records 实时聚合，或明确标注「示例数据」。

P1-1
跨天时段冲突检测恒为 false

extractTimeMinutes 解析「23:00-01:00」得 {start:1380, end:60}，重叠判据 max(start) < min(end) 恒不成立。晚自习延至次日、宿舍查寝等跨天执勤场景会漏报冲突。当前 mock 时段未跨天，属潜伏缺陷。

P1-2
全项目零测试用例，无自动化回归能力

无 *.test.* / *.spec.*，package.json 无 test 脚本。业务不变量（记账、冲突检测）目前靠人工约定保护，任何改动都可能无声破坏。建议优先为 scheduleConflict 与 applyScoreDelta 补单测，二者是纯函数、成本低、价值高。

P1-3
仲裁 adjust 未处理关联整改工单

revoke 已作废工单，但 adjust 分支（DutyContext.tsx:910）只调分、不动工单。分值从 -5 调为 -2 后，班主任仍需按原扣分标准整改，业务口径不一致。

P1-4
排班 status 无任何流转驱动

pending/in_progress/completed 三态仅在 mock 初始化时赋值，全项目无签到、到岗确认、缺岗上报入口。排班→执勤→检查的证据链在「完成」这一步断开，无法回答「该时段谁在岗、是否漏岗」。

P1-5
离线草稿字段缺失，同步后信息不完整

OfflineDraft 仅存 5 个字段，丢失 ruleId / timeSlot / zone / photos。同步时走 createRecord 走默认值填充（rule_hyg_1、recess），现场证据与规则来源全部丢失，且 createdAt 变为同步时刻而非录入时刻，周归属与查重窗口均错位。

P2-1
localStorage 无异常保护，脏数据致白屏

13 处 JSON.parse(localStorage.getItem(...)) 无 try/catch（仅 shifts 有）。任一键值被外部写坏即抛异常，整个应用白屏。仅 shifts 做了校验。

P2-2
Toast 定时器未清理，组件卸载后泄漏

showToast 内 setTimeout 2800ms 未保存句柄、未在 effect cleanup 中 clearTimeout。高频操作下定时器堆积。

P2-3
无 key 的列表渲染与 state 初始化陷阱

ScoreDetailModal 用 useState(targetClassId) 初始化，但 targetClassId 依赖 currentUser。切换身份时组件未重挂载，班主任可能看到上一位班主任的班级数据——权限泄漏。同类问题见 DutyScheduleView。

P2-4
扣分下限无保护，班级分可被扣成负数

applyScoreDelta 无 score ≥ 0 约束。极端情况（多项扣分叠加）班级分为负，「以 100 分为基准」的模型失效。maxScoreDelta 字段已定义但从未使用。

P2-5
结算发布异常不拦截，且统计口径不符

hasAnomalies 仅改变按钮文案为「继续核对发布」，不阻断。带未审记录/未决申诉可一键发布。pendingAppealCount 统计 !== 'resolved'，而 need_more_info 也计入，待补充≠待裁决，口径需明确。

P2-6
SchoolClass 缺 campus 字段

currentCampus 仅为全局展示开关，无数据支撑。切换校区后所有统计、岗位、结算均为同一份数据，多校区能力名不副实。

8. 总体评价

架构健康度良好。三个经过验证的关键设计决策是正确的：积分统一收口到 applyScoreDelta 单一记账入口、时间基准统一到 prototypeClock、通知可见性统一到 isNotifVisible 谓词。这三处收口消除了原型最常见的一类缺陷（同一逻辑散落多处各自实现），说明开发者已具备抽象意识。

上一轮 P0 问题已全部闭环。既有文档列出的 13 项 P0，本次逐条代码验证确认均已修复，且修复方式不是打补丁而是补模型（补 Ledger、补快照、补双轨），方向正确。

当前风险已从「架构性」转为「工程性」。strong>剩余 3 项 P0 全部是工程纪律问题：ID 用时间戳、审核缺幂等、指标写死数据。它们不涉及业务设计，但都会在真实数据下暴露。这是从原型走向可交付产品的正常阶段——业务模型基本正确，剩下的是把不变量用代码和测试固化下来。

最大短板是零测试。系统已经建立了清晰业务不变量（100+Σδ=currentScore、冲突检测语义、双轨并行），但没有任何一条被测试固化。这意味着下一次改动可能无声破坏它们，而这类破坏往往要到真实数据进入、老师质疑分数时才被发现。补 20 个单测的成本，远低于一次成绩争议的排查成本。
